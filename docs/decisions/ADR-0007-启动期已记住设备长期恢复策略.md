# ADR-0007: 启动期已记住设备长期恢复策略

## 背景

应用会在启动后连接 `rememberedDevice`。0.5.6 将首次连接失败与运行中链路丢失共用同一组 5 次退避重连；尝试结束后不再扫描。因此 PC 先启动、灯稍后上电时，已记住设备无法自动恢复，而手动连接仍可成功。

蓝牙 V0.4 §13 的约 60 秒断连宽限期只约束“已建链后短时断开”，不能同时表达“设备尚未上电，客户端长期等待可用”。

## 决策

### D-01 区分两种恢复语义

- `LinkLostRecovery`：已连接设备意外断开，服务硬件宽限期。
- `StartupAvailabilityRecovery`：应用启动时存在已记住设备，但设备当前不可用。

两者共用连接与握手通道，但不共用终止策略。

### D-02 运行中断线保持有限快速重连

`LinkLostRecovery` 继续按 5/10/15/20/25 秒退避尝试 5 次，失败后进入普通离线态。本决策不延长或重新定义硬件 V0.4 §13 宽限期。

### D-03 启动恢复采用快速阶段加长期低频阶段

`StartupAvailabilityRecovery` 首先执行启动首次连接及 5 次快速退避尝试。仍失败后不停止，改为每 60～75 秒执行一次连接，直到成功或被取消。抖动在进程内产生，不写入配置。

### D-04 用户意图拥有最高优先级

恢复任务继续受 `connection_generation` 约束。连接成功、用户主动断开、忘记设备或手动连接另一设备时，旧代次任务必须在下一次等待或连接边界退出，不得重新抢连。

### D-05 不增加用户配置项

长期恢复是“记住设备 + 托盘常驻”的产品语义，不新增开关、重试次数或间隔配置，`config.json` schema 保持不变。

### D-06 连接成功沿用统一装配路径

所有恢复成功都进入 `attach_device`，持久化设备身份、更新快照并调用 `engine.resync()`，不建立第二条连接后处理路径。

### D-07 可恢复失败不永久终止启动恢复

未找到设备、暂无适配器、扫描失败、连接失败或握手失败都记录具体原因并继续长期恢复。用户界面在长期阶段显示“等待设备上线”，不使用持续 spinner，也不反复弹出失败 Toast。

## 备选方案（否决）

| 方案 | 否决原因 |
|---|---|
| 只增大 `MAX_RECONNECT_ATTEMPTS` | 仍有固定失效时刻，且混淆断线宽限与设备可用性 |
| 永久每 5 秒扫描 | 无需要地长期占用 BLE 扫描和系统资源 |
| 前端计时驱动重连 | 关窗后失效，违背 Rust 侧唯一事实源和托盘常驻边界 |
| 把间隔加入配置 | 增加用户心智和 schema 迁移，当前没有产品需求 |

## 后果与验证

- 已记住设备可在应用启动较长时间后上线并自动恢复。
- 最坏自动发现延迟为一个长期间隔加一次扫描/连接时间。
- 纯逻辑测试覆盖快速到长期阶段转换、间隔边界与代次取消。
- BLE 真实上线发现、Windows 登录启动与托盘常驻行为属于 U-01/U-08 实机验证边界。
