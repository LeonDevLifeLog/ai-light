## 背景

AI-Light 客户端需要接收各智能体客户端（Claude Code / Claude / Codex / WorkBuddy / Qoder / Cursor）的运行状态并映射为灯效。调研结论（见调研报告）：各客户端生命周期本质同构，可归约为统一语义；无现成标准可直接套用（ACP 方向相反、AGENT-HOOKS 面向治理）；Claude Code hooks 事件命名已是事实标准。

## 决策

### Q1 标准状态集：5 态 + 开放扩展

**确定：抽象层标准状态集 = `IDLE / WORKING / WAITING / SUCCESS / ERROR`（5 态）**

- 语义：任务生命周期归约——IDLE 兜底无任务；WORKING/WAITING 过程态；SUCCESS/ERROR 终态
- 状态名**开放**：5 态只是内置主题的默认键，自定义状态（如 `REVIEW`）可随时添加，主题映射表驱动
- 来源依据：调研矩阵显示 6 个客户端生命周期均可归约到 5 态；这是覆盖所有客户端的最小完备集

### Q2 终态驻留语义（补充决策）

**确定：SUCCESS/ERROR 默认驻留（保持到下一状态事件），主题可配置 `hold_ms` 自动回落 IDLE**

- 产品语义："状态驻留器"——用户瞄一眼灯即可知道当前状态，而非瞬时确认后熄灭
- 主题格式需含 `hold_ms` 字段（0 = 驻留到下一事件；N = N 毫秒后自动回落）
- 该字段属于主题配置，不进协议（协议只认 SCENE）

### Q3 WorkBuddy：第一期暂缓

**确定：WorkBuddy 第一期不接入，架构预留**

- 原因：腾讯云桌面办公助手，无公开 hooks/事件 API；硬接只能系统级旁路观察（脆弱 hack）；且其生命周期是"项目/交付物"级，与编程 agent 的"回合"级语义不同
- 预留：hook 协议 `source` 字段开放，未来官方开放事件机制时新增适配器即可，客户端本体零改动
- 产品定位声明：第一期 = 编程 agent 生态（Claude Code / Qoder / Codex / Cursor + Claude Desktop 内置 CC）

### Q4 Claude Desktop：纯聊天不覆盖

**确定：Claude Desktop 纯聊天模式不接入；其内置 Claude Code 复用 hooks 正常接入**

- 语义依据：灯对"任务生命周期"敏感，不对"对话过程"敏感；纯聊天只有过程噪音，无任务信号
- 技术依据：Claude Code hooks 在 Desktop 内嵌环境中同样生效（官方文档确认）
- 用户引导：用 Desktop 的 Claude Code 即有灯；纯聊天无灯（产品边界声明）

### Q5 Cursor：第一期暂不接入（08-19 晚调整）

**确定：Cursor 第一期不接入；桥接方案存档为未来选项**

- 调整原因：第一期聚焦配置级接入（Claude Code / Qoder / Codex），避免常驻桥接进程的工程负担（开机自启、崩溃恢复、随 SDK 更新维护）
- 保留选项：`bridges/cursor-bridge`（Node + @cursor/sdk 订阅本地 agent SSE）作为"有 SDK 无 hooks 客户端"的代理模式样板，未来接入时实施
- 接口原则不变：若未来实施，与配置模板适配器**同构**（同一适配器接口的两种实现）

### Q6 本机实测验证（延后）

**确定：本机实测延后至 hook API 正式设计文档（Q7）完成之后、开发启动之前**

- 调整原因：实测对象是 hook API 的消费端，应先定稿 API 规格再实测验证，避免返工
- 实测内容不变：Claude Code HTTP hook 直连（body 格式、Stop vs idle_prompt 时序）、Codex hooks.json + config.toml notify 追加（含 Desktop 重写 notify 冲突 #28404）、Qoder 配置模板
- 产出不变：实测通过后适配器配置模板入 `docs/specs/adapters/`

### Q7 hook API 正式设计文档

**确定：hook API 出正式设计文档 `docs/specs/hook-api.md`；本决策记录只锁定基线**

基线（已锁定）：

- 传输：本地 HTTP 服务，仅监听 127.0.0.1 回环；可选 token（Header）校验，默认关闭
- 端点：`POST /hook`（状态事件）+ `GET /api/status`（只读状态查询）；端口 47800（延续 PCDaemon）
- 请求：`{ "source": "<客户端标识>", "event": "state_change", "state": "<标准态或自定义>", "session": "<可选>", "ts": <可选>, "meta": {…} }`
- 应答：`{ "ok": true, "applied": true, "detail": "…" }`（applied 幂等对账，延续 PCDaemon 应答格式 + V0.4 幂等哲学）
- 正式文档范围：端点定义、事件模型、错误码、幂等与重试、安全、适配器注册约定、示例

### Q8 L2 仲裁规则（确定）

**确定：默认优先级抢占：`ERROR > SUCCESS > WORKING > WAITING > IDLE`，同级按最近活跃；可配置切换为"最近活跃"**

- 语义依据：指示灯的核心语义是"有没有异常/重要的事"，ERROR 永远压过其他状态
- 实现归属：L2 业务层，配置项属于客户端设置（非协议、非主题）

### Q9 会话支持（第一期不做）

**确定：第一期不做会话支持（单灯单会话）；多客户端并发依赖优先级抢占仲裁保证**

- 调整原因：有优先级保证在先，session 不参与业务决策，暂不需要多会话语义
- 预留：hook 请求中的 `session` 字段保留（透传记录），未来需要时启用，不改协议

## 后果

- **正面**：接入层协议基线定型（Q1/Q2/Q7），适配器架构可插拔；第一期全部为配置级接入（Claude Code/Qoder/Codex），无常驻桥接进程，工程负担最小；仲裁规则确定（Q8）后 L2 主逻辑可设计；分层设计保留"每层可单独演进"的期权（未来若出现可观测性标准协议，可整体替换适配器层）
- **负面**：第一期不含 Cursor/IDE 生态用户（暂缓）；Codex WAITING 语义只能近似（无 idle 事件）；Claude Desktop 纯聊天不覆盖
- **待定**：主题格式 schema（含 hold_ms）——待专项沟通；高级直控通道（direct_scene 预留枚举，V2 实现）
