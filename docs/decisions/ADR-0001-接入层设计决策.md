## 背景

AI-Light 客户端需要接收各智能体客户端（Claude Code / Claude / Codex / WorkBuddy / Qoder / Cursor）的运行状态并映射为灯效。调研结论（见调研报告）：各客户端生命周期本质同构，可归约为统一语义；无现成标准可直接套用（ACP 方向相反、AGENT-HOOKS 面向治理）；Claude Code hooks 事件命名已是事实标准。

## 决策

### Q1 标准状态集：5 态 + 开放扩展

**确定：抽象层标准状态集 = `IDLE / WORKING / WAITING / SUCCESS / ERROR`（5 态）**

- 语义：任务生命周期归约——IDLE 兜底无任务；WORKING/WAITING 过程态；SUCCESS/ERROR 终态
- 状态名**开放**：5 态只是内置主题的默认键，自定义状态（如 `REVIEW`）可随时添加，主题映射表驱动
- 来源依据：调研矩阵显示 6 个客户端生命周期均可归约到 5 态；这是覆盖所有客户端的最小完备集

### Q2 终态驻留语义（补充决策）

**确定：SUCCESS/ERROR 默认驻留（保持到下一状态事件），主题可配置 `hold_ms` 自动回落 IDLE**

- 产品语义："状态驻留器"——用户瞄一眼灯即可知道当前状态，而非瞬时确认后熄灭
- 主题格式需含 `hold_ms` 字段（0 = 驻留到下一事件；N = N 毫秒后自动回落）
- 该字段属于主题配置，不进协议（协议只认 SCENE）

### Q3 WorkBuddy：第一期暂缓

**确定：WorkBuddy 第一期不接入，架构预留**

- 原因：腾讯云桌面办公助手，无公开 hooks/事件 API；硬接只能系统级旁路观察（脆弱 hack）；且其生命周期是"项目/交付物"级，与编程 agent 的"回合"级语义不同
- 预留：hook 协议 `source` 字段开放，未来官方开放事件机制时新增适配器即可，客户端本体零改动
- 产品定位声明：第一期 = 编程 agent 生态（Claude Code / Qoder / Codex / Cursor + Claude Desktop 内置 CC）

### Q4 Claude Desktop：纯聊天不覆盖

**确定：Claude Desktop 纯聊天模式不接入；其内置 Claude Code 复用 hooks 正常接入**

- 语义依据：灯对"任务生命周期"敏感，不对"对话过程"敏感；纯聊天只有过程噪音，无任务信号
- 技术依据：Claude Code hooks 在 Desktop 内嵌环境中同样生效（官方文档确认）
- 用户引导：用 Desktop 的 Claude Code 即有灯；纯聊天无灯（产品边界声明）

### Q5 Cursor：cursor-bridge 桥接进程（第一期交付物）

**确定：Cursor 接入通过官方 SDK 桥接进程实现，为第一期交付物**

- 位置：ai-light 仓库 `bridges/cursor-bridge/`（Node，@cursor/sdk 订阅本地 agent SSE 事件流）
- 接口要求：与配置模板适配器**同构**（同为"翻译到标准状态"的两种实现），便于未来 Cursor 原生 hooks 支持后无缝退役
- 可复用：作为"有 SDK 无 hooks 客户端"的代理模式样板（Windsurf / Trae 等可复制）

### Q6 本机实测验证

**确定：开发前本机实测三客户端，实测通过后适配器配置模板入仓库 `docs/specs/adapters/`**

| 实测项 | 验证内容 | 产出 |
|---|---|---|
| Claude Code | HTTP hook 直连（请求 body、事件时序：Stop vs idle_prompt） | `claude-code.settings.json` 模板片段 |
| Codex | hooks.json + config.toml notify 追加；Desktop 重写 notify 冲突（#28404）实测 | `codex.hooks.json` + `codex.config.toml` 追加 |
| Qoder | 安装 CLI，验证事件与 Claude Code 差异 | `qoder.settings.json` 模板片段 |

### Q7 hook 协议形态（基线确认）

**确定：本地 HTTP 服务，`POST http://127.0.0.1:47800/hook` + `GET /api/status`（端口延续 PCDaemon 47800）**

- 请求：`{ "source": "<客户端标识>", "event": "state_change", "state": "<标准态或自定义>", "session": "<可选>", "ts": <可选>, "meta": {…} }`
- 应答：`{ "ok": true, "applied": true, "detail": "…" }`（applied 幂等对账，延续 PCDaemon 应答格式 + V0.4 幂等哲学）
- 安全：仅监听 127.0.0.1 回环；可选 token（Header）校验，默认关闭
- 只读接口：`GET /api/status` 返回当前业务状态、设备连接、电量、版本

## 后果

- **正面**：接入层协议定型，适配器架构可插拔；新客户端接入 = 新增适配器，客户端本体零改动；分层设计保留"每层可单独演进"的期权（未来若出现可观测性标准协议，可整体替换适配器层）
- **负面**：Cursor 桥接进程是第一期唯一的代码级适配器（常驻进程、随 SDK 更新维护）；Codex WAITING 语义只能近似（无 idle 事件）
- **待定**：L2 仲裁规则（优先级抢占 vs 最近活跃）、会话支持范围（单会话为主/多会话可配置）、高级直控通道（direct_scene 预留枚举，V2 实现）
