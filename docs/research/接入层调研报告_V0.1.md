# AI-Light 接入层调研报告：智能体客户端生命周期与 Hook 机制

| 项目 | 内容 |
|---|---|
| 文档版本 | V0.1 |
| 调研目的 | 为 L1 接入层（hook 协议与抽象层）设计提供事实依据，不拍脑袋 |
| 调研对象 | Claude Code / Claude(Desktop) / Codex(CLI+Desktop) / WorkBuddy / Qoder / Cursor |
| 调研日期 | 2026-08-19 |
| 方法论 | 官方文档 + 社区实现 + 本机 CLI 实测（claude 2.1.31 / codex 0.147.0 已安装） |

---

## 1. 核心结论（TL;DR）

1. **Claude Code 的 hooks 事件命名已成为事实标准**：Qoder（及阿里通义灵码等）直接复刻同一套事件名（SessionStart/Stop/PreToolUse/PostToolUse/Notification…），且 Claude Code hooks 原生支持 **HTTP endpoint** 作为 handler——意味着"零脚本直连"成为可能。
2. **各客户端生命周期可以归约为同一套语义**：会话（Session）、回合（Turn）、等待（Waiting）、完成（Success）、失败（Error）、子任务（Task）。差异只在命名与触发时机，不在本质。
3. **没有统一标准可直接套用**：ACP（Agent Client Protocol）面向 IDE↔agent 双向通信（方向相反）；Microsoft AGENT-HOOKS-0.1 面向企业治理；两者都不适合直接作为状态灯的输入协议，但**状态枚举定义可借鉴**。
4. **接入难度分三档**：
   - 🟢 原生 hooks（Claude Code / Qoder / Codex）→ 配置即可
   - 🟡 需小适配器（Cursor，用官方 SDK 订阅本地 agent 事件）
   - 🔴 无公开 hook（WorkBuddy / Claude Desktop）→ 待确认或暂缓

## 2. 各客户端生命周期与 Hook 机制

### 2.1 Claude Code（本机 2.1.31）🟢

**Hook 机制**：`~/.claude/settings.json`（用户级）或项目 `.claude/settings.json`，`hooks` 组按事件配置。Handler 类型支持 **command / http / mcp-tool / prompt / agent** 五种。**HTTP 类型可直接 POST 到本地服务**，这是对我们最友好的路径。

**关键生命周期事件**（31+，按与状态灯的相关性排序）：

| 事件 | 触发时机 | 灯效语义 |
|---|---|---|
| `UserPromptSubmit` | 用户提交提示词 | → WORKING（开始干活） |
| `Stop` | Claude 完成响应 | → SUCCESS（回合结束） |
| `StopFailure` | 回合因 API 错误终止 | → ERROR |
| `Notification`(matcher=`idle_prompt`) | Claude 空闲等待用户输入 | → WAITING |
| `Notification`(matcher=`permission_prompt`) | 等待用户批准权限 | → WAITING（权限） |
| `PreToolUse` / `PostToolUse` | 工具调用前后 | 细化（可选） |
| `SubagentStart` / `SubagentStop` | 子代理启停 | 细化（可选） |
| `TaskCreated` / `TaskCompleted` | 任务创建/完成 | → WORKING / SUCCESS |
| `SessionStart` / `SessionEnd` | 会话启停 | → IDLE 边界 |
| `Elicitation` | 主动向用户提问 | → WAITING |
| `TeammateIdle` | 团队代理空闲 | → WAITING |

**事件输入格式**：stdin JSON（command 类型）或 HTTP POST body，含 `session_id`、`transcript_path`、`hook_event_name`、`cwd` 等。

### 2.2 Codex CLI + Desktop（本机 0.147.0）🟢

**Hook 机制**：`~/.codex/hooks.json`（或项目 `.codex/hooks.json`），事件集较小且演进中（v0.114 引入，目前已有 SessionStart / SessionEnd / Stop / UserPromptSubmit / PreToolUse / PostToolUse / PermissionRequest）。仅 `command` 类型（curl 即可）。

**Notify 机制**（独立于 hooks）：`~/.codex/config.toml` 的 `notify` 数组，**任务结束（turn-ended）时调用**。**本机已配置**：`notify = [..., "turn-ended"]`（被 Codex Desktop 包装成 SkyComputerUseClient）。→ 可再追加我们的 curl。

**相关事件**：

| 事件 | 触发时机 | 灯效语义 |
|---|---|---|
| `UserPromptSubmit` | 用户提交 | → WORKING |
| `Stop` | 回合结束 | → SUCCESS / ERROR（按退出码） |
| `notify`(turn-ended) | 任务结束 | → SUCCESS / ERROR |
| `PreToolUse`/`PostToolUse` | 工具调用前后 | 细化（可选） |
| `PermissionRequest` | 请求权限 | → WAITING（权限） |

**注意**：Codex Desktop 会重写 `notify`（包装为 Computer Use），落地时需验证与 Desktop 的兼容（GitHub issue #28404 有已知冲突）。

### 2.3 Cursor（IDE，含 Local Agent / Cloud Agents）🟡

**无 hooks 机制**（IDE 不是 CLI agent）。官方接入路径：

1. **Cursor SDK（@cursor/sdk，本地 agent）**：可编程控制本地 agent，SSE 事件流：`status`（RUNNING / FINISHED / ERROR）、`assistant`（文本增量）、`tool_call`（running/completed）、`permission` 等。
2. **Cloud Agents API**：云端 agent，`POST /v1/agents` 创建 run，SSE 事件同构（RUNNING/FINISHED/ERROR），支持断点续传（Last-Event-ID）。

**接入方案**：写一个轻量 Node 适配器（`cursor-bridge`），用 SDK 订阅本地 agent 事件 → 翻译后 POST 到 AI-Light 本地服务。与 CLI hooks 相比多一个常驻小进程，但事件粒度更细。

### 2.4 Qoder（CLI / IDE / QoderWork）🟢

**Hook 机制（2026-09-05 按官方文档与本机发行版复核）**：国际版用户级配置为 `~/.qoder/settings.json`，国内版为 `~/.qoder-cn/settings.json`；项目还可使用 `.qoder/settings.json`（共享）/ `.qoder/settings.local.json`（本机），桌面端与 CLI 使用兼容的 Hooks。事件覆盖工具、任务、权限、子智能体、上下文、配置、文件和 Worktree 生命周期；handler 支持 `command / http / prompt / agent`。stdin 公共字段含 `session_id` / `cwd` / `hook_event_name` / `agent_id` 等。

**结论**：Adapter `0.1.5` 已通过 command handler 正式接入并只管理用户级配置；沿用现有 runtime 发现、短期 Token、日志和失败开放机制，不为 Qoder 单独建立 HTTP 配置路径。

### 2.5 WorkBuddy（腾讯云桌面 AI Agent 办公助手）🔴

**性质确认**：桌面 AI 办公工作台（非编程 CLI），基于腾讯 CodeBuddy 架构，多 Agent 并行、自然语言任务交付，支持 Skills/连接器/IM 集成（微信、企微、飞书、钉钉）。

**Hook 现状**：未检索到公开的本地 hooks / 事件 API 文档。桌面闭源应用，可观测性低。

**接入策略（待确认）**：
- 方案 A：等待/推动官方开放事件机制（长期）
- 方案 B：系统级旁路观察（进程/窗口/通知）——hack，不推荐
- 方案 C：**暂缓**，第一期不做 WorkBuddy，架构预留（推荐）

### 2.6 Claude（Desktop 应用）🟡

**Hook 现状**：消费级聊天应用，无独立本地 API / hooks。但其**内置 Claude Code 集成**（Desktop 中运行 Claude Code 时 hooks 同样生效——官方文档明确："sessions in the terminal, IDE extensions, the Desktop app, and Claude Code on the web all fire the same hook events"）。

**接入策略**：
- 方案 A：引导用户在 Claude Desktop 中使用内置 Claude Code 完成 agent 任务 → 复用 Claude Code hooks 接入（实际可行，需用户行为配合）
- 方案 B：仅接入 Claude Code（含 Desktop 内嵌），Claude Desktop 纯聊天模式暂不覆盖（推荐作为边界声明）

## 3. 生命周期语义对比矩阵

| 语义 | Claude Code | Codex | Qoder | Cursor(SDK) | 建议标准态 |
|---|---|---|---|---|---|
| 会话开始 | SessionStart | SessionStart | SessionStart | —（agent 创建） | —（上下文） |
| 会话结束 | SessionEnd | SessionEnd | SessionEnd | — | —（上下文） |
| **开始干活** | UserPromptSubmit / TaskCreated | UserPromptSubmit | UserPromptSubmit / TaskCreated | run 开始 (status RUNNING) | `WORKING` |
| **完成** | Stop / TaskCompleted | Stop / notify(turn-ended) | Stop / TaskCompleted | status FINISHED | `SUCCESS` |
| **失败** | StopFailure / PostToolUseFailure | Stop(非0退出) | StopFailure / PostToolUseFailure | status ERROR | `ERROR` |
| **等待用户** | Notification(idle_prompt) / Elicitation | （无，缺口） | Elicitation / TeammateIdle | permission 事件 | `WAITING` |
| **等待权限** | Notification(permission_prompt) | PermissionRequest | PermissionRequest | permission 事件 | `WAITING` |
| 工具调用中 | PreToolUse/PostToolUse | 同 | 同 | tool_call | 细化（可选） |
| 子代理 | SubagentStart/Stop | — | SubagentStart/Stop | — | 细化（可选） |

**缺口发现**：
- Codex **没有**"等待用户输入"的独立事件（只有 turn 结束 + 权限请求）→ WAITING 语义在 Codex 上只能近似（回合结束且未完成 = 等待？或 PermissionRequest）
- Cursor SDK 事件最细（可直接推"思考中/调用工具/等待"），但需要常驻适配器
- 各客户端对"SUCCESS vs WAITING"的判定需要**适配器层消歧**（例如：Claude Stop 后可能是在等用户回复，也可能是任务完成——`Stop` 语义需与 `idle_prompt` 联合判断）

## 4. 抽象层设计草案（接入层架构）

### 4.1 两层模型：标准状态集 + 客户端适配器

```text
┌─────────────────────────────────────────────────────┐
│  AI-Light 客户端（Tauri）                            │
│                                                     │
│  ┌─────────────────────────────────────────────┐    │
│  │ L1 接入层                                   │    │
│  │  HTTP Server (127.0.0.1:47800)              │    │
│  │  ┌───────────────────────────────────────┐  │    │
│  │  │ 标准事件模型（状态无关协议）            │  │    │
│  │  │  state: WORKING/SUCCESS/ERROR/WAITING │  │    │
│  │  │  + source + session + meta            │  │    │
│  │  └───────────────────────────────────────┘  │    │
│  └─────────────────────────────────────────────┘    │
│              ▲              ▲              ▲        │
│        HTTP hook      HTTP hook       HTTP hook     │
│   ┌─────────┐   ┌─────────┐   ┌──────────┐          │
│   │ClaudeCode│   │ Qoder   │   │ Codex    │  🟢 配置即用│
│   └─────────┘   └─────────┘   └──────────┘          │
│        ▲                                            │
│   ┌─────────┐   ┌─────────┐   ┌──────────┐          │
│   │cursor-  │   │ 其它新  │   │ MCP 反向 │  🟡 适配器 │
│   │bridge   │   │ 客户端  │   │ (预留)   │          │
│   └─────────┘   └─────────┘   └──────────┘          │
└─────────────────────────────────────────────────────┘
```

**设计原则**：
1. **协议层只认标准状态**（5 态 + 扩展），不认识任何客户端专属事件名；
2. **每个客户端 = 一个适配器**：🟢 类适配器 = 一份 hooks 配置模板（让用户粘贴）；🟡 类适配器 = 一个小桥接进程（仓库提供）；
3. **新客户端接入** = 新增适配器（配置模板或桥接脚本）+ 注册 `source` 标识，客户端本体零改动；
4. 状态名开放（主题映射表驱动），标准 5 态只是内置主题的默认键。

### 4.2 标准状态集（v1 草案）

| 状态 | 含义 | 默认灯效建议 |
|---|---|---|
| `IDLE` | 无活跃任务 | 熄灭 / 常亮低亮度 |
| `WORKING` | AI 正在执行 | 呼吸蓝/绿 |
| `WAITING` | 等待用户输入/权限 | 缓慢闪烁黄 |
| `SUCCESS` | 任务完成 | 绿色常亮（短时） |
| `ERROR` | 任务失败 | 红色闪烁（+蜂鸣） |

> 状态集合与 V0.4 SCENE 完全解耦：主题文件里 `WORKING → SCENE{...}` 随意映射，5 态只是默认主题的键；自定义状态（如 `REVIEW`）随时可加。

### 4.3 Hook 协议（草案，与 PCDaemon 47800 端口延续）

```http
POST http://127.0.0.1:47800/hook
Content-Type: application/json

{
  "source": "claude-code",          // 客户端标识（适配器注册名）
  "event": "state_change",
  "state": "WORKING",               // 标准状态或自定义状态
  "session": "task-001",            // 可选：会话标识
  "ts": 1724040000000,              // 可选：事件时间
  "meta": { "detail": "running tests", "progress": 60 }
}
```

应答：`{"ok": true, "applied": true, "detail": "..."}`（applied 对账幂等，沿用 PCDaemon 应答格式 + V0.4 幂等哲学）

### 4.4 各客户端适配器落地方案

| 客户端 | 适配器类型 | 具体做法 |
|---|---|---|
| Claude Code | 🟢 配置模板 | `~/.claude/settings.json` 加 hooks：`UserPromptSubmit→WORKING`、`Stop→SUCCESS`、`StopFailure→ERROR`、`Notification(idle_prompt/permission_prompt)→WAITING`，handler 用 **http** 类型直连 |
| Qoder | 🟢 Adapter CLI | `~/.qoder/settings.json` 幂等合并 AI-Light command hooks；桌面端与 CLI 共用，子智能体事件过滤 |
| Codex | 🟢 配置模板 | `hooks.json`（UserPromptSubmit/Stop/StopFailure→ERROR 近似）+ `config.toml notify` 追加 turn-ended；注意 Desktop 重写 notify 的冲突 |
| Cursor | 🟡 桥接进程 | `cursor-bridge`（Node，@cursor/sdk 订阅本地 agent SSE）→ POST 标准事件；Cloud Agents API 作为可选云端源 |
| Claude Desktop | 🟡 引导 | 引导用户用内置 Claude Code（hooks 自动生效）；纯聊天模式暂不覆盖 |
| WorkBuddy | 🔴 暂缓 | 架构预留 source 注册，待官方开放事件机制 |

## 5. 风险与待确认项

1. **Codex WAITING 缺口**：无 idle 事件，WAITING 需近似（PermissionRequest + 回合未结束判定），语义可能不精确 → 适配器内做启发式，文档注明局限
2. **Codex Desktop notify 重写冲突**（GitHub #28404）：Desktop 启动时会包装 notify 为 Computer Use，需实测验证我们的追加是否保留
3. **Claude Code HTTP hook**：官方支持但相对较新，需实测（fallback：command 类型 curl）
4. **WorkBuddy 接入**：暂缓 or 推动官方？需昻哥决策
5. **Claude Desktop 纯聊天模式**：明确不覆盖（边界声明），用户需使用内置 Claude Code 才能点亮灯
6. **多源并发**：多个客户端同时工作时状态冲突 → 由 L2 仲裁处理（优先级抢占），source 字段为仲裁提供依据
